# Прямая покупка подписки с лендинга

Дата: 29 октября 2026. Статус: проект для согласования, продуктовый код не изменён.

## Цель и границы

Покупатель выбирает Basic / Pro / Max и период на сайте, входит в Monetize, оплачивает подписку и устанавливает Chrome-расширение. После входа в тот же аккаунт расширение получает оплаченный доступ. Покупается подписка для Chrome на компьютере; веб-демо сохраняет отдельные бесплатные ограничения.

Free ведёт в Chrome Web Store. Платные карточки ведут на `/subscribe/?plan=starter|pro|max&interval=month|year`. Пакеты минут остаются в расширении. Не меняем цены, квоты, сроки возврата, production-каталог и правила переноса минут. Реальные списания не входят в проверку.

Уточнение пользователя: после входа под почтой покупки действующая оплаченная подписка должна включать всё поведение оплаты Tier 1/2, даже если сохранённый country_tier=3. Это касается сайта и расширения. Пользователь также указал на необходимость аккаунтов в Monetize и нашей базе. Monetize создаёт/находит аккаунт через auth flow; наша база делает upsert по проверенному auth_user_id до checkout. Не создавать новый Monetize-аккаунт для каждой покупки и не связывать доступ только по присланной клиентом почте.

## Оплаченный доступ поверх Tier 3

После успешного входа проверяем покупки Monetize, при необходимости восстанавливаем локальный доступ через lifecycle, затем отдаём согласованный account context. До завершения проверки показываем загрузку, без ложного Free/Tier 3 экрана и предложения повторно заплатить. Введённый email без успешного входа ничего не открывает.

Нужен единый backend-признак effective billing access: подтверждённая действующая оплаченная подписка ИЛИ существующий operator force_paywall ИЛИ обычный доступ Tier 1/2. Действующая подписка определяется доступом и сроком, включая отменённое автопродление до оплаченной даты; past_due, неподтверждённый checkout и устаревшее plan в БД не подходят. Регион не меняет уже оплаченный доступ.

Для paid Tier 3 показывать тариф/период, баланс и обновление квоты, управление подпиской, Extra Minutes и допустимые upgrades точно как для paid Tier 1/2. Yearly по-прежнему нельзя покупать повторно. Если подразумевается полное равенство с Tier 1/2, бесплатный дополнительный пул также использует их cap/cadence при следующем положенном обновлении, без сброса или повторной выдачи минут при входе. Это предложение исполнителя по деталям бесплатного пула; текущие оплаченные квоты не меняются.

Не выставлять постоянный force_paywall и не переписывать country_tier из-за покупки. Предлагаемое поведение после реального прекращения оплаченного доступа: снова применять исходные правила региона, сохраняя Extra Minutes и историю платежей; управление задолженностью/поддержка не исчезает из-за региона. Сам факт прошлой покупки не создаёт бессрочную льготу. Доступность первой покупки для Tier 3 этим уточнением не расширяется.

Изменения нужны в `routes/transcribe.ts` (сейчас can_purchase учитывает только tier/force), `useBillingStore.ts` (сейчас geo override учитывает только force), API/account store и зависимых AccountView/PlanPicker/MinutePackModal/UserMenu. Новый серверный признак обхода **регионального** ограничения проверять только для текущего авторизованного аккаунта. Не обходить disabled paywall или недоступность провайдера. После logout/смены аккаунта сбрасывать его немедленно.

Обязательные проверки: новый пользователь сайта без расширения; existing paid Tier 3 после логина; delayed webhook с восстановлением до показа аккаунта; canceled-but-unexpired Tier 3; yearly Tier 3 без повторной покупки; past_due/expired Tier 3; logout и вход другого пользователя; отсутствие повторной выдачи free/paid минут.

## Проверенные исходные данные

- Лендинг: Astro static + Vue. Все карточки сейчас используют `InstallButton`. `public/payment-success.html` без проверки платежа сообщает Payment received и предлагает вернуться в расширение.
- PR #11 открыт, не merged при проверке. Ветка этой работы `codex/landing-direct-checkout` создана от его HEAD `64a7905`; исходная ветка не изменяется. Перед PR ещё раз проверить merge: если #11 открыт — зависимый PR, если merged — перенести только новые изменения на актуальный main. Чужие untracked документы и изображения не включать.
- Установленный Monetize SDK в расширении — 3.4.0. `AuthClient` поддерживает email/password, OTP и OAuth. Сайт и расширение имеют отдельное хранилище сессий; автоматической общей сессии нет. Один paywall 860 и API origin `https://platform.audio-to-text-transcription.com` должны использоваться в обоих клиентах.
- Backend проверяет Bearer через Monetize `/user`, получает доверенный `auth_user_id`. Сейчас middleware при ошибке превращает пользователя в anonymous: новые платёжные маршруты обязаны затем явно возвращать 401/503, а не продолжать анонимно.
- `getOrCreateUser` создаёт/находит пользователя при обращениях расширения. Webhook не создаёт пользователя; lifecycle требует существующую строку. `restore-purchases` тоже не создаёт её. Поэтому регистрация в Monetize сама по себе недостаточна: строка нашего аккаунта должна быть создана до checkout.
- `useBillingStore` перед checkout проверяет баланс, `can_purchase` и `canPurchasePlan`, затем передаёт `ignoreActivePurchase:true` (Monetize учитывает даже free как активную покупку). Эти ограничения сейчас находятся в клиенте.
- `canPurchasePlan`: без плана доступны все тарифы; с monthly — более высокий тариф monthly/yearly либо тот же yearly; с yearly — новая покупка запрещена.
- Наличие `plan=null` не доказывает отсутствие подписки: past_due очищает план. Проверять также lifecycle и историю провайдера, включая отменённое автопродление с ещё действующим доступом.
- Восстановление покупок уже использует серверный SDK, блокировку пользователя, ревизию lifecycle и одноразовый перенос остатка monthly → yearly. Однако отсутствие restorable purchase сейчас даёт manual review; нельзя вызывать этот маршрут автоматически для каждого нового посетителя.
- `/transcribe/plan-prices` отдаёт annual только по флагу и `X-Extension-Version>=1.22.0`. Сайт не должен представляться расширением. Нужен отдельный web-каталог с собственным разрешением annual. CORS текущего backend отдельно проверить/настроить для сайта; preview-маршруты имеют собственную политику.
- Сведения о включённом annual flag и отправке 1.22.0 на модерацию получены из передачи контекста, повторной проверки production в этой работе не было. Rollout-документ в основном репозитории содержит устаревшее состояние flag=false.

## Подходы

1. **Рекомендуемый: вход на сайте + серверный checkout.** Сайт использует существующий Monetize AuthClient, backend создаёт checkout только после проверки аккаунта и перехода. Требует изменений двух репозиториев, зато объединяет проверку доступа и восстановление.
2. Вход на сайте + браузерный BillingClient.createCheckout. Меньше серверной работы, но создание локального аккаунта всё равно необходимо; ограничения переходов и повторной покупки остаются в браузере. Не соответствует требованию надёжных проверок нового web-потока.
3. Гостевая покупка с последующим присоединением к аккаунту. SDK технически поддерживает guest/anonymous, но текущая система доступа не проверена для такого сценария; потребуется отдельный механизм подтверждения и присоединения покупки. Не предлагается для первой версии.

Выбор первого подхода пока является рекомендацией исполнителя, а не подтверждённым решением пользователя.

## UX

### Выбор и вход

На платных карточках `Get Basic / Get Pro / Get Max`, Free — `Add to Chrome`. Общий переключатель сохраняет выбранный период в ссылке. Перед переходом виден полный годовой платёж.

Страница подписки содержит краткий заказ и явный текст: **“For the Chrome extension on your computer. This subscription does not increase the website demo limits.”** На мобильном этот текст остаётся видимым; покупка разрешена для последующего использования на компьютере.

Рекомендация: основной вход по email и шестизначному коду через AuthClient.sendOtp/verifyOtp. Предусмотреть обычный вход в существующий аккаунт средствами SDK для пользователей с паролем/OAuth; способы не включать принудительно, брать доступные настройки paywall. Не предлагать guest. Сессия без подтверждённой переносимой идентичности не получает checkout. Совпадение email само по себе не считать доказательством объединения разных аккаунтов; проверка identity между вебом и расширением обязательна в sandbox.

Builder check выявил конкретный пробел: текущий backend verifier возвращает только id/email/profile/geo, без достоверного anonymous/email-confirmed признака. Перед реализацией выбрать проверяемое на сервере доказательство: документированные поля Monetize user/auth introspection либо верифицированные JWT claims с проверкой подписи/issuer/audience (никогда простое decode). Если такой источник недоступен, сервер должен сам проксировать OTP verify и фиксировать подтверждённый вход для этой identity; способ выбрать по результатам sandbox. Клиентский is_anonymous и наличие строки email не заменяют доказательство. На запуске включать только способы входа, для которых проверено получение того же auth_user_id в опубликованном расширении; неподтверждённый способ скрывать. Если ни один способ не прошёл — web checkout остаётся закрыт, установка расширения доступна.

После входа показываем “Subscription for {email}” и `Use another account`. Переключение аккаунта очищает заказ, статус и незавершённые запросы прежнего пользователя. Сохранять можно выбранные plan/interval, но не его баланс или checkout URL. Не пересылать токены в URL или в расширение.

### Подтверждение заказа

Показываем тариф, квоту каждые 30 дней, полную сумму и период, автопродление, условия возврата со ссылкой. Для Pro yearly: “$119.99 billed annually · 7,200 minutes every 30 days”. Применимые налоги/локальная валюта должны быть согласованы с итоговой страницей провайдера; при изменении каталога просим подтвердить обновлённую сумму.

Кнопка: `Continue to secure payment`. Это явное действие после входа, а не автоматический переход из auth callback. Для monthly → yearly отдельное подтверждение: полная годовая сумма списывается сейчас, текущая подписка заменяется после успешной оплаты, остаток оплаченных monthly минут переносится в Extra, квота запускается заново.

| Текущее состояние | Действие сайта |
| --- | --- |
| Нет оплаченной подписки, данные проверены | Покупка любого доступного тарифа |
| Monthly, тот же monthly или ниже | Текущий план/управление, без новой оплаты |
| Monthly → более высокий monthly | Явное подтверждение upgrade, правила как в расширении |
| Monthly → тот же или выше yearly | Подтверждение полной годовой оплаты и переноса остатка |
| Yearly с действующим доступом | Показать подписку и управление; повторная покупка запрещена |
| Автопродление отменено, срок ещё не истёк | Считать подписку действующей и применять ту же матрицу |
| Past due / incomplete / неоднозначные подписки | Управление оплатой или поддержка; новую покупку блокировать |
| Истёкшая подписка, провайдер подтвердил отсутствие действующей | Разрешить новую покупку |
| Ошибка проверки / недоступность / неизвестная цена или интервал | Повторить проверку, без checkout |
| Региональное ограничение без действующего платного доступа | Объяснение недоступности, установка бесплатного расширения |
| Tier 3 с подтверждённой действующей подпиской | Полный платёжный интерфейс как Tier 1/2, обычная матрица переходов |

### Возврат после оплаты

Для сайта использовать отдельный `/subscription-result/`, поскольку расширение наблюдает URL с префиксом `/payment-success` и закрывает свою checkout-вкладку. Существующий адрес сохранить совместимым с расширением. Сам переход на страницу не является доказательством оплаты.

Состояния: `Checking your subscription` → подтверждённый план либо `Still confirming` с повторной проверкой и восстановлением. `Subscription active` показывать только после серверной проверки соответствия аккаунта, выбранного price/interval и применённого доступа. При задержке не предлагать оплатить ещё раз.

После подтверждения: 1) `Add to Chrome`; 2) открыть расширение; 3) войти тем же способом в `{email}`. Показать действующий план и `Manage subscription`. Если сессия потеряна — вход и серверное восстановление; query string не подтверждает покупку. Веб-демо не разблокируется.

Отмена у провайдера возвращает к заказу. Она не доказывает, что платежа нет: перед новой попыткой повторно проверить провайдера и незавершённый заказ.

## Серверный контракт и безопасность данных

Предлагаемые маршруты под `/account/web-billing`, отдельно от `/web` demo и fingerprint/transcription middleware:

- `GET /context`: строгая авторизация; создание аккаунта по проверенному auth_user_id без fingerprint; профиль, текущий доступ, актуальные цены, допустимые переходы, причина блокировки, версия состояния. Ответы no-store.
- `POST /checkout`: plan, interval, подтверждённая версия предложения и intent ID. Не принимать от клиента доверенные email/userId, цену, redirect URL или ignoreActivePurchase. Повторно проверить provider + local lifecycle + доступность продажи; использовать серверный каталог и фиксированные return URLs.
- `GET /intents/:id`: только владелец; pending/confirmed/review/failed со сверкой server-authoritative доступа, без платёжных реквизитов.
- `POST /restore`: целевое восстановление; переиспользовать lifecycle/transfer сервисы. `No purchases` для нового пользователя — нормальный результат, не поток операторских алертов. Не вызывать восстановление каждые пять секунд.
- `POST /portal`: клиент SDK на сервере с проверенной identity и фиксированным return URL; для недоступного портала — контакт поддержки.

Создание аккаунта: отдельная функция ensureAuthenticatedAccount, атомарный upsert по уникальному auth_user_id; fingerprint=NULL, anon_minutes_left=0. Применять ту же начальную free-квоту и country/tier, что у getOrCreateUser, ровно один раз. Не менять tier/баланс существующего пользователя. Проверить гонку первого входа с одновременным запуском расширения.

Для checkout создавать новый BillingClient на запрос, привязывать проверенные userId и email; не использовать изменяемую общую identity между запросами. Секрет API остаётся на сервере. Передавать IP только из доверенной цепочки прокси. Проверка `/user` учитывает X-Client-Ip, но документация предупреждает, что targeting/pricing checkout разрешаются отдельно: эквивалентность браузерному региональному поведению является обязательной проверкой перед выпуском. Нельзя принимать клиентский флаг visibility/forcePaywall как разрешение.

Хранить purchase intent в БД до внешнего вызова: владелец, target price/interval, сумма/валюта, lifecycle revision, стабильный provider idempotency key, статус и timestamps. При параллельных кликах/вкладках возвращать тот же незавершённый intent/URL, разные цены до разрешения текущего intent блокировать. Сетевой таймаут не создаёт новую попытку: повторять со старым ключом. Создание intent и проверку revision сериализовать на пользователя; внешнюю сеть не держать внутри долгой транзакции. После внешнего ответа заново проверить revision, прежде чем отдавать URL.

Нельзя считать старую hosted-сессию недействительной только потому, что пользователь закрыл вкладку или истёк локальный таймер. До разрешения нового intent необходимо подтвердить терминальное состояние/истечение у провайдера. Способ проверки старой сессии в SDK/API пока не установлен: исследовать в sandbox до реализации завершённой retry-логики; если нет надёжного способа — pending + resume/support, без выпуска второго URL. Уже выданные checkout из старого расширения не контролируются этим web-intent: абсолютную гарантию против оплаты двух старых ссылок нельзя заявлять без проверки provider semantics и обновления всех каналов.

`ignoreActivePurchase` вычисляет сервер только после подтверждённого отсутствия оплаченной подписки (с учётом free-конфликта Monetize) либо допустимого, явно подтверждённого upgrade. Не повторять любой 409 с override вслепую.

Новые маршруты ограничить rate limits, размером JSON, конкретными origin сайта и согласованных sandbox preview. Не менять CORS демо. Не логировать Bearer, OTP, email в аналитике, checkout/portal URLs. Аналитика: plan, interval, stage, безопасный код результата; success только по подтверждённому доступу.
