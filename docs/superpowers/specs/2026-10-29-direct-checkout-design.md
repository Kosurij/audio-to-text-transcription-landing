# Прямая покупка подписки с лендинга

Дата: 29 октября 2026. Согласовано пользователем: первая покупка по email без кода; вход нужен для управления подпиской и в расширении. Этот документ заменяет первоначальный вариант с обязательным входом перед покупкой.

## Пользовательский путь

1. Free ведёт в Chrome Web Store. Basic / Pro / Max передают выбранный тариф и период на `/subscribe/`.
2. На странице заказа покупатель вводит email и видит полный платёж за месяц или год, количество минут каждые 30 дней, автопродление, налоги и условия. Код и пароль для первой покупки не нужны.
3. Backend получает цену из собственного каталога Monetize, создаёт checkout с `ignoreActivePurchase: false`. Monetize создаёт или находит пользователя по email и возвращает его ID. Backend создаёт отсутствующую строку `users` до выдачи платёжной ссылки.
4. После оплаты покупатель устанавливает расширение и входит с той же почтой. Оплаченный доступ появляется через существующие баланс и webhook. Подписка предназначена для Chrome на компьютере; лимиты веб-демо независимы.
5. Для проверки, восстановления и изменения действующей подписки на сайте есть отдельный вход по email-коду. Сам вход никогда не инициирует оплату.

API Monetize требует email до создания hosted checkout, поэтому поле находится на странице заказа. Ввод email не является авторизацией и не даёт доступа к данным аккаунта.

## Учётная запись и оплаченный Tier 3

Основной ключ — подтверждённый `auth_user_id`, общий с расширением. Email сам по себе не позволяет читать баланс, открывать portal или менять существующий план. У гостевой покупки сервер доверяет ID из ответа провайдера, а при потерянном ответе — ID из подписанного события настроенного paywall.

Новые guest-строки имеют `fingerprint=NULL`, `anon_minutes_left=0`; страна/тир заполняются первым проверенным входом. UPSERT и обработка конфликта уникальности гарантируют одну строку и один начальный бесплатный пул при одновременном входе с сайта и расширения. Известная география и существующие остатки при входе не сбрасываются.

Существующий ответ `force_paywall` вычисляется как сохранённый ручной флаг ИЛИ действующий оплаченный доступ. Поэтому подписчик Tier 3 видит план и те же платёжные возможности, что Tier 1/2. Отмена автопродления сохраняет доступ до оплаченной даты. После истечения или утраты оплаченного доступа действует обычная политика тира; ручной флаг не изменяется автоматически.

## API и границы доверия

`/account/web-billing` подключается до общего HTTP logger/CORS и fingerprint middleware. Использует отдельные лимиты запросов, JSON 4 KiB, точный список Origins, `Cache-Control: no-store`, ответы без секретов и сырых ошибок провайдера.

Публичные операции:

- `GET /config`: enabled, paywallId и apiOrigin без API key.
- `GET /catalog`: разрешённые сервером тарифы и версия предложения.
- `POST /guest-checkout`: только email, plan, interval, version, случайный guestToken. Не принимает userId, цену, return URL или override от клиента.
- `POST /auth/otp/send|verify`: proxy только фиксированных OTP endpoint. При успешном verify дополнительно проверяет access token через Monetize и совпадение user ID/email, сохраняет подтверждение почты.

Операции с Bearer:

- `GET /context`, `POST /restore`: создать/обновить профиль, проверить подписки у провайдера, безопасно согласовать баланс и вернуть актуальный аккаунт/каталог.
- `POST /checkout`: разрешённое изменение тарифа после свежей проверки подписки, версии цены и подтверждения email.
- `POST /portal`: управление подпиской текущей идентичности.
- `GET /intents/:id`: только собственная платёжная попытка и подтверждённое состояние.

Используется SDK AuthClient 3.4.0 для браузерной сессии. Сервер создаёт отдельный BillingClient для каждого запроса каталога/подписок/portal. Checkout использует REST, поскольку SDK не возвращает необходимый для guest bootstrap userId.

## Повторные запросы и подписки

До сетевого вызова сохраняются уникальный intent, ключ идемпотентности и полный неизменяемый payload провайдера. Блокировки и частичные уникальные индексы допускают одну незавершённую попытку на email и аккаунт. У гостя хранится только SHA-256 случайного 256-bit токена браузера; другой браузер не получает ссылку или данные аккаунта по одной почте.

Повтор после timeout использует тот же ключ и тело. Другая цена при незавершённом checkout отклоняется. После 23 часов неизвестного результата новая сессия автоматически не создаётся: требуется проверка. При наличии сохранённой ссылки её можно возобновить. Попытка не освобождается по одному возврату с платёжной страницы или локальному таймеру.

Для авторизованных изменений сохраняется существующая политика расширения: yearly повторно не покупается; monthly разрешает повышение тарифа либо тот же тариф на год. Списание за год полное; оплаченный остаток месячного тарифа переносится один раз существующим `annualPlanTransfer`. Замена и restore используют существующие lifecycle locks. Неоднозначные, past_due и неподтверждённые состояния блокируют новую покупку.

Подтверждение результата требует нового provider subscription ID относительно baseline, совпадения тарифа/периода и текущего оплаченного доступа. Обычный просмотр аккаунта тоже завершает подтверждённый intent, даже если покупатель не открывал страницу результата. Redirect сам по себе не доказывает оплату.

## Интерфейс

`/subscribe/` и `/subscription-result/` имеют noindex. Главная страница не загружает auth SDK заранее. При выключенном флаге платные CTA сохраняют установку расширения. Новые покупки и управление имеют разные переключатели: выключение checkout не лишает доступа к status/restore/portal.

Смена аккаунта и выход очищают состояние и инвалидируют незавершённые запросы. Страница результата гостя предлагает установку и вход в расширении; статус «active» показывается только после серверной проверки. Авторизованный результат опрашивается каждые 5 секунд до двух минут, затем остаются ручная проверка и восстановление.

## Проверка и выпуск

Код по умолчанию выключен (`WEB_BILLING_ENABLED=false`, `PUBLIC_WEB_BILLING_ENABLED=false`). Backend разворачивается раньше лендинга. Цена/лимиты берутся из server mapping; sandbox ID не добавляются в production.

Проверки покрывают покупку без OTP, управление после входа, paid Tier 3, истечение/ошибку платежа, отмену автопродления, две вкладки, повтор после timeout, смену аккаунта, stale catalog, поддельный результат, подписанный webhook до первого входа и конкурентное создание аккаунта. PostgreSQL тесты используют только явно заданную disposable `subscription_test` и отдельную схему.

В sandbox 912 Stripe TEST подтверждены создание checkout по email, наличие userId и повтор с тем же ключом/URL без оплаты. Ответ `/user?user_id=` не содержит identity, поэтому он не доказывает совпадение с email-login. До включения нужны полный тест оплаты и входа в расширении на контролируемой почте, проверка опубликованной версии расширения и managed Polar parity. Live paywall 860, реальные платежи и production настройки в этой задаче не изменяются.
